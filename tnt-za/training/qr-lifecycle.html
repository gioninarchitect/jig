Phase 1 — QR Code Generation
When a plant is registered

Plant QR Code

Every time a cultivator registers a new plant, the system automatically generates:

The QR encodes a URL. When scanned by any smartphone camera (not just TnT-ZA), it opens the plant record directly. When scanned inside the TnT-ZA app, it triggers the full workflow.

When a container is registered

API endpoints

How to Get a QR Code

  • GET /api/qr/plant/:id — Returns QR PNG URL + data URL for a plant
  • GET /api/qr/container/:id — Returns QR for a container
  • GET /api/qr/batch/:id — Returns QR for a batch
  • GET /api/qr/print/:type/:id — Returns raw PNG image (for printing)

On the frontend: every plant detail, container detail, and batch detail page has a "Print QR Label" button that downloads the PNG.

Phase 2 — Print & Attach Labels
Physical labelling

Printing QR Labels

Download the QR PNG from the app. Print using:

  • Thermal label printer (recommended) — Waterproof, adhesive-backed, 50x50mm labels
  • Regular printer — Print on adhesive paper, cut to size, laminate if needed
  • Handwritten backup — If no printer: write BIN-001 on the container with permanent marker. The AI Vision can read handwritten text too.
Where to stick them

Label Placement

  • Plant tags: On the stake/clip next to the plant, facing outward for easy scanning
  • Bins: On the front face, upper-left corner, above the fill line
  • Racks: On the end panel, one label per rack level
  • Bags: On the seal/tie area, visible when bags are stacked
  • Jars: On the lid or side, not on the bottom

Labels must be visible without moving the container. If you have to flip, rotate, or open something to scan — the label is in the wrong place.

Step-by-Step Detail
Step 1

Scan the Container Label

Staff opens the Scan & Weigh page from the sidebar. Taps "Scan Label". The rear camera opens.

They point the phone at the QR label on the container. Tap the green capture button. The photo is sent to Claude AI Vision which:

  • Reads the QR code or text identifier from the image
  • Determines the type: plant (ZA-XXXXXX), container (BIN-XXX), batch (B-YYYY-NNN), or scale
  • Looks up the entity in the database
  • Returns the full record: type, status, zone, last weight, handler

Time: 2-3 seconds.

Step 2

Select Action

For containers, the system shows 4 action buttons:

  • LOAD — Product goes INTO the container. Used when harvesting into a bin.
  • UNLOAD — Product comes OUT of the container. Used when moving to processing.
  • MOVE — Container moves to another zone (e.g., Grow Room → Drying Room). Requires selecting destination zone.
  • HANDOVER — Container transfers from one person to another. Both handler IDs are recorded.

For plants: the system shows "View Details" which opens the plant page where you can transition phases.

Step 3

Photograph the Scale

After selecting an action, staff must record the weight. Two options:

Option A: Photo (recommended) — Tap "Photograph Scale". Camera opens again. Point at the digital scale display. Capture. Claude Vision reads the number and unit (grams or kilograms) from the display using OCR. The weight auto-fills.

Option B: Manual — Tap "Enter manually". Type the weight on the numeric keypad. Used when photo fails or no digital scale is available.

Tips for clear scale photos: Ensure display is well-lit (no glare). Hold phone steady and straight-on. Wait for scale to stabilize before photographing. Include only the display in frame.
Step 4

Review Weight & Variance

The confirmation screen shows:

  • Container ID and selected action
  • The new weight (from scale photo or manual entry)
  • The previous weight (from the last recorded event on this container)
  • The variance percentage calculated automatically

If variance is within the expected range, a green indicator shows: "4.1% loss — within range"

If variance exceeds the threshold, a red warning shows before the staff member can submit:

"26.3% weight change detected." 650.2g → 479.1g. This will trigger a CRITICAL anomaly alert to all senior staff. You may still submit — but the alert will fire immediately.

The warning does not block submission. The staff member can still confirm. But they know the alert will fire. This is by design — we want real data, not data people are afraid to enter.

Step 5

Confirm & Record

Staff taps the green confirm button. The system creates:

  • A ContainerEvent record: container ID, event type, weight, weight unit, handler ID (from JWT), zone, timestamp
  • An AuditLog entry with SHA-256 hash chain (tamper-evident, append-only, never deletable)
  • If zone changed: updates the container's currentZoneId
  • If action is HANDOVER: records both outgoing handler (the person submitting) and incoming handler (selected by the submitter)

The screen shows "Recorded" with a green checkmark and two buttons: "Scan Next" (loops back to step 1) and "View Timeline" (opens the container detail page).

Phase 4 — Weight Variance Detection
Automatic comparison

How Variance Is Calculated

On every UNLOAD, MOVE, or HANDOVER event, the system:

  • Finds the last recorded weight for this container (most recent event with a weight value)
  • Calculates: variance = (previousWeight - newWeight) / previousWeight
  • Looks up the threshold for this container type
  • If variance exceeds threshold → triggers anomaly
Container TypeExpected LossAlert ThresholdReason
BIN~0%>5%Short-term storage, no moisture loss expected
BAG~0%>5%Sealed, trimmed product
JAR~0%>5%Cured, sealed product
RACK~10-15%>15%Drying racks — moisture loss is expected and normal
PACKAGE~0%>5%Final packaged product

Drying racks have a higher threshold (15%) because cannabis naturally loses 10-15% of its weight during the drying process (moisture evaporation). Anything beyond 15% is suspicious.

When threshold is exceeded

What Happens on Alert

The system executes ALL of the following simultaneously:

  • Anomaly record created — type: CONTAINER_WEIGHT_VARIANCE, severity: HIGH or CRITICAL (>25% = CRITICAL)
  • Notification to ALL senior roles — every user with role FACILITY_MANAGER, TENANT_ADMIN, or SUPER_ADMIN in this tenant receives a notification
  • Audit log entry — action: ANOMALY_DETECTED, with before/after weights, linked to the container
  • Event bus emission — ANOMALY_DETECTED event fires for any subscribed systems
  • Dashboard red panel — the anomaly appears immediately in the red "Weight Variance Alerts" panel on the dashboard
THIS IS NOT OPTIONAL. The alert cannot be suppressed, deferred, or dismissed. It is created automatically by the system. The ONLY way to clear it is for a Facility Manager (or higher) to investigate and resolve it with written investigation notes.
Resolution process

Resolving a Weight Variance Anomaly

To resolve an anomaly, a Facility Manager must:

  • Go to Compliance → Open Anomalies
  • Click Resolve on the anomaly
  • Enter investigation notes (mandatory — cannot be blank). Examples:
Legitimate reason
"Scale was not zeroed before weighing. Re-weighed after calibration: 648.1g. Within 0.3% of expected."
Concerning finding
"Product spill during transfer. Approximately 30g recovered from floor and returned to container. CCTV footage reviewed and confirms."

Investigation notes are permanent. They are stored in the audit trail and included in compliance reports. SAHPRA inspectors can read them.

Phase 5 — Chain of Custody
Every event is recorded

The Full Trail

Every container event records:

Who
Handler ID (from JWT — the logged-in user)
What
LOAD, UNLOAD, MOVE, WEIGH, or HANDOVER
When
Timestamp (automatic, cannot be faked)
Where
From zone → To zone
How much
Weight in grams, scale photo URL
Verified by
SHA-256 hash chain (tamper-evident audit log)

For HANDOVER events, both the outgoing handler (person giving) and incoming handler (person receiving) are recorded. This creates an unbroken chain: "Johan loaded 650g into BIN-001 at 09:15 in Grow Room → handed to Lerato at 09:22 → Lerato moved BIN-001 to Drying Room at 09:30 with weight 648g → unloaded at 14:45 with weight 562g (13.3% loss — within drying range)."

Phase 6 — Batch Weight Reconciliation
Macro-level check

Harvest Weight vs Current Total

The reconciliation endpoint compares:

  • Batch harvest weight — total weight of all plants when they were harvested into this batch
  • Current container weight — sum of the last recorded weight across all containers linked to this batch
  • Variance — the difference, as a percentage

This catches systemic issues that individual container checks might miss. If 5 containers each lost 4% (under threshold individually), but the batch total is down 20%, something is wrong.

Endpoint: GET /api/containers/reconciliation/:batchId

Other Anomaly Types (Beyond Weight)

CONTAINER_ZONE_MISMATCH

▼

Triggered when a container is scanned in a zone different from its recorded currentZoneId.

Example: BIN-001 is recorded as being in Grow Room, but someone scans it in Storage. Either the container was moved without recording, or someone is in the wrong room.

Notifies: Facility Manager + Tenant Admin

CONTAINER_STALE

▼

Triggered when a LOADED or IN_TRANSIT container has no events for more than 24 hours.

Example: JAR-002 was loaded yesterday and has had no activity since. Is it stuck in curing? Was it forgotten? Is the label damaged?

Check endpoint: GET /api/anomalies/check-stale

Notifies: Facility Manager

INVENTORY_DISCREPANCY

▼

Triggered during SAPS destruction events. If the weight recorded in the destruction log differs from the batch/plant recorded weight by more than 2%.

Example: Batch B-2026-003 has a recorded weight of 1,200g. During destruction, 1,150g is weighed by the SAPS officer. That's a 4.2% discrepancy. Where did 50g go?

Notifies: Facility Manager + Tenant Admin + Super Admin

TRANSPORT_TIME

▼

Triggered when a transport manifest's actual duration exceeds 130% of the expected duration.

Example: A transport from ILCO Farm to a collection point has an expected duration of 180 minutes. The vehicle arrives after 260 minutes (144% of expected). What happened during the extra 80 minutes?

Notifies: Facility Manager + Security Officer

Why This Matters — SAHPRA Compliance

What SAHPRA requires

▼

Under Section 22C(1)(b), cannabis cultivators must maintain:

  • Full traceability — every gram must be accounted for from cultivation to sale or destruction
  • Batch labelling — all batches must have unique identifiers as early as possible in the process
  • Record retention — audit records must be kept for at least 10 years
  • Destruction records — all destruction must be witnessed by a SAPS officer
  • INCB reporting — quantities produced, manufactured, used, and destroyed must be reported to the International Narcotics Control Board

The QR + Scan + Weigh system satisfies ALL of these requirements automatically. No manual paperwork. No Excel spreadsheets. No gaps.

During a SAHPRA inspection

▼

An inspector can:

  • Scan any QR label on any container or plant → instantly see the full history
  • Verify the audit trail → the SHA-256 hash chain proves no entries have been tampered with
  • Check weight reconciliation → batch harvest weight vs current container total
  • Review anomaly log → see every variance, how it was investigated, and what was found
  • Export audit CSV → download the complete trail for offline analysis
  • Verify the hash chain → GET /api/audit/verify returns { valid: true } if no tampering

All of this from a phone. No office visit required. No waiting for someone to pull files.

Technical: What Gets Stored

ContainerEvent record (per scan)

▼
{
  id:                "uuid",
  eventType:         "MOVE",
  weight:            623.4,
  weightUnit:        "g",
  notes:             null,
  photoUrl:          "/uploads/scans/scan-1711450200.jpg",
  timestamp:         "2026-03-26T09:30:00Z",
  containerId:       "uuid → BIN-001",
  fromZoneId:        "uuid → Grow Room",
  toZoneId:          "uuid → Drying Room",
  outgoingHandlerId: "uuid → Johan van Wyk",
  incomingHandlerId: null (only set for HANDOVER)
}

AuditLog entry (per action)

▼
{
  id:         "uuid",
  action:     "CONTAINER_MOVED",
  entityType: "Container",
  entityId:   "uuid → BIN-001",
  beforeJson: { zone: "Grow Room", weight: 650.2 },
  afterJson:  { zone: "Drying Room", weight: 623.4 },
  hashChain:  "a3f8b2c9d1e4...  (SHA-256)",
  timestamp:  "2026-03-26T09:30:00Z",
  userId:     "uuid → Johan van Wyk",
  tenantId:   "uuid → ILCO Farms"
}

The hashChain field = SHA256(previousEntryHash + timestamp + userId + action + entityId). If ANY previous entry is modified, every subsequent hash breaks. This is cryptographic proof that the trail has not been tampered with.

Anomaly record (when triggered)

▼
{
  id:                  "uuid",
  type:                "CONTAINER_WEIGHT_VARIANCE",
  severity:            "CRITICAL",
  description:         "Container BIN-001 weight: 650.2g → 479.1g (26.3% loss, threshold 5%)",
  entityType:          "Container",
  entityId:            "uuid → BIN-001",
  detectedAt:          "2026-03-26T14:45:00Z",
  resolvedAt:          null,
  resolvedById:        null,
  investigationNotes:  null,
  falsePositive:       false,
  tenantId:            "uuid → ILCO Farms"
}

This record CANNOT be deleted. It can only be resolved (with mandatory notes). If it was a false positive (e.g., scale error), the FM marks falsePositive: true with an explanation. The record still exists — it just shows it was investigated and explained.
